## 1. Описание функциональности монолитного приложения

### Классы пользователей приложения Smart Home

Пользователи приложения разделяются, согласно текущей документации, на 2 класса:

- Конечные пользователи (далее - пользователи) - клиенты компании производителя ПО
- Сотрудники компании-производителя (далее - монтажники)

### Области функциональности приложения Smart Home

Исходя из исходного кода существующего приложения, в нем существует одна функциональная область - управление датчиками физических величин (далее за физическую величину, по умолчанию, будем принимать температуру, хотя, технически, возможно использование и датчиков других физических величин практически без изменения функциональности приложения - потребуется одно изменение - добавление других Типов Сенсоров в models/sensor.go:11).

Под термином "управление" понимаем как CUD операции над сущностью Датчик, так и получение его текущих значений (Read операции).

Приведенные методы API приложения работают только в упомянутой функциональной области:

- `GET /health` - Health check - общий endpoint проверки запущенности приложения, который всегда отдает 200ОК (main.go:39)
- `GET /api/v1/sensors` - Get all sensors - получение всех объектов с данными о датчиках, дополнительно вызывается внешний сервис получения температуры датчиков по их id (handlers/sensor.go:46)
- `GET /api/v1/sensors/:id` - Get a specific sensor - получение объекта с данными о конкретном датчике по его идентификатору, дополнительно вызывается внешний сервис получения температуры датчиков по их id (handlers/sensor.go:73)
- `POST /api/v1/sensors` - Create a new sensor - создание нового объекта-датчика (models/sensor.go:28 + handlers/sensor.go:132)
- `PUT /api/v1/sensors/:id` - Update a sensor - Обновляет информацию о датчике
- `DELETE /api/v1/sensors/:id` - Delete a sensor - Удаляет датчик
- `PATCH /api/v1/sensors/:id/value` - Update a sensor's value and status - Обновляет значение параметра датчика и его статус.

Определение DDL БД сервиса Smart home содержит только одну таблицу sensors, что также не позволяет сделать вывод о наличии дополнительных областей функциональности в приложении.

**Управление датчиками, расположенными в некоторой локации**

- Пользователи могут (предположительно, т.к. кода фронта нет)
  - просматривать текущее значение датчика по его идентификатору (хотя не очень понятно, как именно они его получат, возможно, от монтажников?)

- Система поддерживает
  - Работу с сущностью Датчик (CRUD операции);
  - Получение температуры из внешнего источника-сервиса


### Выявленные первичные недостатки

Представлен некий общий список, при необходимости, может быть разделен на блоки и приоритизирован.

1. Технически никто не мешает пользователям приложения выполнять функции монтажников и управлять самим сущностями Датчики внутри приложения
2. Получение данных по /api/v1/sensors приводит в опросу всех зарегистрированных датчиков в синхронном режиме, что может заняться длительное время и спровоцировать таймаут, и не оптимально, как минимум, потому что можно не опрашивать датчики со статусом "inactive"
3. sensors.GET("/temperature/:location", h.GetTemperatureByLocation) - не зарегистрирован в postman коллекции, а также не упомянут в документации 
4. `PATCH /api/v1/sensors/:id/value` - совмещение 2х действий в одном методе: и обновление температуры и обновление статуса датчика. Такое совмещение может вызваться сложности, как минимум, при управлении статусами датчиков. 
5. Хранение данных в одной таблице не позволяет реализовать функциональность хранения истории изменений параметров датчиков
6. Отсутствует разделение прав доступа к датчикам разных пользователей, атака с вектором перебора всех id датчиков позволит получать значения произвольных датчиков других пользователей и, что важнее, управлять их статусами. Монтажники могут выдавать себя за Пользователей.
7. Отсутствует связка сущности Датчик с сущностью Пользователь, что приводит к огромному количеству проблем.
8. Различный стиль API получения температуры из внешнего сервиса. В запросе по id - REST, в запросе по location - что-то смешанное, нет указания на конкретный датчик, поэтому в общем случае может вернуться множество значений, например, для "кухня".
